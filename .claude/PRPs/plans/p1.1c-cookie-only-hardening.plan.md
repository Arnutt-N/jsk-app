# Plan: P1.1c Cookie-Only Hardening (PR 2C)

## Summary

Remove Bearer fallback, tighten `SameSite=Lax` → `Strict`, drop token
body copies, and delete the `COOKIE_AUTH_MODE` + `NEXT_PUBLIC_COOKIE_AUTH`
flags — cookie auth becomes the only auth. The hardening is dormant
behind the still-`dual` env until ops flips to cookie-only; the deploy
order is **frontend-first** (the opposite of 2A) because 2C is a strict
*subset* of 2B behavior (it removes a path).

## User Story

As an admin-console operator, I want the admin app to accept only
HttpOnly `SameSite=Strict` cookies for auth (no Bearer fallback, no
token-in-body leak), so that an XSS or a cross-site navigation cannot
exfiltrate or send my session credentials after the dual-mode rollout
has proven stable.

## Problem → Solution

`dual` mode keeps Bearer fallback, `Lax` SameSite, and token body
copies — all three are the attack surface that cookie auth was supposed
to close. After the 3-5 day observation window passes with zero
`auth.refresh_reuse_detected` audit rows, PR 2C removes all three and
deletes the gating flags so the dual/bearer modes exist only as a
documented rollback path.

## Patterns to Mirror

### COOKIE_SAMESITE_SINGLE_SOURCE (the FR2 mechanism)

```python
# SOURCE: backend/app/core/cookie_auth.py:28,39-46
COOKIE_SAMESITE = "lax"  # <-- the ONE line FR2 changes to "strict"

def _cookie_kwargs(*, path: str, max_age: int) -> dict:
    return {
        "path": path,
        "max_age": max_age,
        "httponly": True,
        "secure": settings.is_production_like,
        "samesite": COOKIE_SAMESITE,  # flows to both set + delete
    }
```
**Why this matters:** changing one constant flips `set` AND `delete`
attributes in lockstep. Do NOT introduce a separate
`COOKIE_SAMESITE_DELETE` — a mismatch silently no-ops the delete in
browsers, leaving the old cookie in place (the exact bug PR 2A test 7
guards against). FR2 is a one-line edit + a test that introspects the
`Set-Cookie` header on both login and logout.

### TOKEN_SOURCE_STILL_TRACKED (the FR1 mechanism)

```python
# SOURCE: backend/app/api/deps.py:55-67 (before FR1)
if settings.COOKIE_AUTH_MODE in ("dual", "cookie"):
    cookie_token = request.cookies.get(ACCESS_COOKIE)
    if cookie_token:
        token, token_source = cookie_token, "cookie"

if token is None and settings.COOKIE_AUTH_MODE != "cookie":
    if credentials and credentials.credentials:
        token, token_source = credentials.credentials, "bearer"

request.state.auth_token_source = token_source  # CSRF gate keys on this
```
After FR1, the `token_source` is always either `"cookie"` or `None`
(no Bearer path means no `"bearer"` source). The CSRF gate at
`deps.py:146-153` (`if token_source == "cookie" and request.method in
_CSRF_PROTECTED_METHODS`) keeps working unchanged — it now fires on
*every* cookie-authenticated mutating request, which is the intended
end state. Do NOT touch the CSRF gate; only touch the resolution block.

### BODY_OMIT_ALWAYS (the FR3 mechanism)

```python
# SOURCE: backend/app/api/v1/endpoints/auth.py:321,471 (before FR3)
body_omitted = settings.COOKIE_AUTH_MODE == "cookie"
# ... later:
return {"user": user, "csrf_token": csrf} if body_omitted else {...tokens...}
```
After FR3, `body_omitted = True` unconditionally — the `if/else`
collapses to the cookie-only branch. The `csrf_token` body field STAYS
(it's not a credential, it's the double-submit header value the client
keeps in memory per PR 2B FR2). Only `access_token` / `refresh_token`
keys are removed from the body.

### FLAG_REMOVAL_ZERO_DRIVE_BY (the FR5 mechanism)

```typescript
// SOURCE: frontend/lib/authFetch.ts (2B shape, before FR5)
const COOKIE_AUTH = process.env.NEXT_PUBLIC_COOKIE_AUTH === 'true';
// ... branch: if (COOKIE_AUTH) { cookie path } else { bearer path }
```
After FR5, the `COOKIE_AUTH` constant + the `else` branch are deleted.
The cookie path becomes the unconditional body. **Grep-proof
requirement** (FR6 test 12): after the edit, `rg "NEXT_PUBLIC_COOKIE_AUTH"
frontend/` returns zero hits. Same for `Authorization: Bearer` injection
sites — only the deleted migration code used it, and the migration code
is also removed in FR5 (it's part of the 2B flag-gated path).

## Risks & mitigations

| Risk | Mitigation |
|------|-----------|
| Stale `COOKIE_AUTH_MODE=dual` on Koyeb crashes 2C backend startup (`extra="forbid"`) | Task 4 verifies the `model_config` extra policy FIRST; if `forbid`, add ignore entry before any other task |
