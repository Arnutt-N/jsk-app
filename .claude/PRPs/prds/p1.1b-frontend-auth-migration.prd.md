## Problem (verified in PR 2A PRD §Problem + current frontend code)

Admin auth stores `access_token`/`refresh_token` in `localStorage`
(`frontend/contexts/AuthContext.tsx:220-224,285,303-305`) — any XSS exfiltrates
long-lived credentials. Auth state is *inferred* from token presence
(`isAuthenticated = !!user && !!token`, line 337) instead of an explicit server
check, so a stale/expired token in localStorage looks "authenticated" until a
request 401s. No `credentials: 'include'` and no `X-CSRF-Token` header exist
anywhere in the frontend (grep-verified — zero hits). The WebSocket sends the
raw long-lived JWT as its first message (`frontend/hooks/useWebSocket.ts:37,50`)
and connects cross-origin direct to the backend host
(`frontend/lib/websocket/wsUrl.ts:21-23`), bypassing the Vercel rewrite — so it
can never use SameSite cookies and needs the single-use ticket that PR 2A built
(`POST /auth/ws-ticket`).

PR 2A shipped the backend dual-mode foundation dark (default `bearer`, zero
behavior change). PR 2B is the frontend half: adopt cookies, CSRF, server-side
session bootstrap, single-flight refresh, one-time Bearer→cookie migration, and
ticket-based WebSocket auth.

## Scope decision (binding)

This is **PR #2 of the recorded 3-PR design**. Frontend migrates from
Bearer+localStorage to cookie auth. The backend must be flipped to
`COOKIE_AUTH_MODE=dual` (an ops action gated by `docs/remediation/migration-controls.md`)
at the same time the frontend flag is enabled — dual mode sets cookies AND
returns body tokens, so a not-yet-updated frontend keeps working during the
overlap. PR 2C later flips to `cookie`-only and removes the flags. No production
flag flip is forced by this PR's code — it ships behind
`NEXT_PUBLIC_COOKIE_AUTH=false` (default) so the deploy is dark.

## Functional Requirements

### FR1 — Centralized credentialed API client

The fetch interceptor (`frontend/lib/authFetch.ts`) gains a cookie-auth mode,
gated by `NEXT_PUBLIC_COOKIE_AUTH === 'true'` (evaluated once at module load).
In cookie mode:
- Every request gets `credentials: 'include'` so HttpOnly auth cookies are sent
  cross-origin (CORS is already `allow_credentials=True`, env-supplied origins).
- NO `Authorization` header is injected — cookies carry the access token.
- The legacy Bearer-injection path is preserved verbatim for when the flag is
  off (zero behavior change for not-yet-flipped environments).

### FR2 — CSRF token in memory + double-submit header

A new module-level in-memory CSRF store (`frontend/lib/csrfStore.ts`) holds the
token returned by login/refresh/me response bodies. It is NEVER persisted to
localStorage (an XSS that can read memory can already call fetch; persisting it
adds exfil risk with no benefit). The fetch interceptor attaches `X-CSRF-Token`
to every state-changing request (POST/PUT/PATCH/DELETE) in cookie mode. On page
reload the token is bootstrapped from `GET /auth/me` (which echoes `csrf_token`
when cookie-authenticated — `auth.py:506-509`).

### FR3 — Auth state machine (loading | authenticated | unauthenticated)

`AuthContext` models auth as an explicit state machine, NOT inferred from token
presence. On mount: state = `loading` → call `GET /auth/me` (credentials:
include) → `authenticated` (200, store user + CSRF) or `unauthenticated` (401).
`isAuthenticated` is true ONLY when state === `authenticated`. This eliminates
the "stale localStorage token looks authenticated" class of bugs.

### FR4 — One-time Bearer→cookie migration

On first load after deploy, if legacy `localStorage.auth_token` exists, call
`POST /auth/migrate-session` with `Authorization: Bearer <legacy_access_token>`
(the endpoint is Bearer-only by construction — `auth.py:67,385`). On success:
clear ALL legacy localStorage auth keys (`auth_token`, `auth_refresh_token`,
`auth_user`), then bootstrap from `/auth/me`. On failure (401/409/429/network):
clear legacy keys and go `unauthenticated` (user re-logs in). Migration runs at
most once per browser — after clearing localStorage the trigger is gone.
Guarded by the cookie-auth flag (only migrates when flag is on).

### FR5 — Single-flight refresh (CRITICAL — round-2 N3)

Refresh uses `POST /auth/refresh` with `credentials: 'include'` (the refresh
cookie, scoped to `/api/v1/auth`, is sent automatically; NO Authorization
header). Concurrent 401s MUST share a single in-flight refresh promise — reuse
the existing `inflightRefresh` mechanism in `authFetch.ts:19,29-42`. This is
non-negotiable: the backend's strict rotation marks the old refresh token
`rotated` on first use; a second concurrent refresh would see it as `rotated`
→ `REUSE_DETECTED` → revoke the ENTIRE session family
(`auth_session_service.py` RotationOutcome.REUSE_DETECTED). Single-flight
guarantees exactly one rotation call per refresh wave. The refresh handler
updates the in-memory CSRF token from the response body.

### FR6 — Logout via cookie clear + family revoke

`POST /auth/logout` with `credentials: 'include'` → backend clears cookies +
revokes family (`auth.py:337-382`). Frontend clears in-memory CSRF, sets state
to `unauthenticated`, redirects to `/login`. No localStorage cleanup needed
(none stored in cookie mode). Idempotent (backend returns 204 even with no
cookies). Broadcasts logout to other tabs (FR8).

### FR7 — WebSocket ticket auth

The live-chat WebSocket no longer sends the long-lived access JWT. Instead:
fetch `POST /auth/ws-ticket` (credentials: include) → receive `{ticket,
expires_in}` → send `ticket` as the WS auth message. On reconnect, mint a fresh
ticket (single-use — a replayed ticket is rejected by `authenticate_ws_user`).
This works cross-origin (WS bypasses Vercel rewrite, connects direct to backend
— `wsUrl.ts:21-23`) because the ticket is a short-lived single-use credential,
not an ambient cookie. The existing JWT-as-first-message path is preserved when
the cookie-auth flag is off.

### FR8 — Multi-tab logout / expiry sync

When one tab logs out or its session expires, other open tabs must not stay
authenticated. Use `BroadcastChannel('jsk:auth')` (with `storage` event
fallback for browsers lacking BroadcastChannel) to broadcast `logout` /
`expired` events. Each tab's AuthContext listens and transitions to
`unauthenticated` + redirects to `/login`. The existing per-tab
`jsk:auth-expired` CustomEvent (same-tab, `authFetch.ts:48-53`) is preserved for
the same-tab case; the BroadcastChannel covers cross-tab.

### FR9 — Frontend env flag for safe rollout

`NEXT_PUBLIC_COOKIE_AUTH` (boolean, default `false`). When `false`: current
Bearer+localStorage behavior is byte-identical to today (FR1 legacy path, no
CSRF, no migration, JWT-WS). When `true`: full cookie-auth behavior (FR1-FR8).
- **Owner:** backend ops + frontend deploy coord.
- **Rollback:** redeploy with `NEXT_PUBLIC_COOKIE_AUTH=false` (Next.js PUBLIC
  env is build-time — document in migration-controls.md).
- **Removal:** PR 2C (after observation window, removes the flag + Bearer path).
- **Threshold:** enable after backend `COOKIE_AUTH_MODE=dual` is confirmed live;
  monitor login/refresh success + reuse-detection audit rows for 3-5 days.

### FR10 — Tests

New Vitest unit tests covering:
1. Bootstrap from `/auth/me`: 200 → authenticated + CSRF stored; 401 →
   unauthenticated.
2. CSRF attachment: POST/PUT/PATCH/DELETE get `X-CSRF-Token`; GET does not.
3. Single-flight refresh: N concurrent 401s → exactly ONE `/auth/refresh` call;
   all N retried with the refreshed session.
4. One-time migration: legacy `localStorage.auth_token` → `/auth/migrate-session`
   called once → localStorage cleared → bootstrap.
5. Migration failure (401/409): localStorage cleared → unauthenticated.
6. Logout: `/auth/logout` called → state unauthenticated → redirect.
7. Multi-tab sync: BroadcastChannel `logout` → listener tab unauthenticated.
8. Reload: in-memory CSRF lost → `/auth/me` re-bootstraps it.
9. Refresh failure → logout (no family revoke from the frontend side).
10. Flag off: zero behavioral diff vs main (Bearer path, no CSRF, no migration).

## Non-Goals

- Flipping `COOKIE_AUTH_MODE` on the backend (ops action, gated by
  `migration-controls.md`) — this PR ships the frontend code only.
- Removing the Bearer legacy path, SameSite=Strict, flipping to `cookie`-only
  mode — PR 2C.
- RBAC/permission changes (PR 2D), media signing (PR 2E).
- Server-side scheduler for session retention (P1.6 — NEW-2 index is the
  interim fix already merged in PR #134).
- Changing the WS transport (still cross-origin direct-to-backend; only the
  auth credential changes from JWT to ticket).
- LIFF auth (separate flow, not admin cookie auth).

## Rollout note (PR body)

Ships dark: `NEXT_PUBLIC_COOKIE_AUTH` defaults to `false`, so deploying this PR
changes nothing until the flag is enabled. Rollout sequence:
1. Deploy frontend PR 2B (flag off — behavior unchanged).
2. Ops: flip backend `COOKIE_AUTH_MODE` → `dual` (sets cookies + keeps body
   tokens — old frontend still works).
3. Ops: redeploy frontend with `NEXT_PUBLIC_COOKIE_AUTH=true`.
4. Observe 3-5 days (login/refresh success, reuse-detection audit rows = 0).
5. PR 2C: flip backend to `cookie`-only, remove frontend flag + Bearer path.
Rollback at any step: step 2 → flip backend back to bearer; step 3 → redeploy
frontend with flag false. No migration is destructive (legacy localStorage is
cleared client-side only; backend tolerates both until PR 2C).
