## Problem (verified in `docs/remediation/preflight-evidence-and-designs.md` §2-§3)

Admin auth stores `access_token`/`refresh_token` in `localStorage`
(`frontend/contexts/AuthContext.tsx:185-224`) — any XSS anywhere in the admin
app exfiltrates long-lived credentials. Refresh tokens are stateless 7-day JWTs
(`backend/app/core/security.py:95-119`): they cannot be revoked, rotated, or
reuse-detected. Zero cookie/CSRF code exists in the backend (grep-verified §2).
The WebSocket sends the same long-lived JWT as its first message
(`backend/app/api/v1/endpoints/ws_live_chat.py:102-119`) with no Origin check,
and WS connects **directly to the Koyeb host, bypassing the Vercel rewrite**
(`frontend/lib/websocket/wsUrl.ts:1-32`) — so it is cross-origin in production
and can never use SameSite cookies; it needs a ticket. `COOKIE_AUTH_MODE`
(`backend/app/core/config.py:40`, `bearer|dual|cookie`, default `bearer`) landed
in PR 0A but is wired to nothing. CORS is already credentialed
(`backend/app/main.py:177` `allow_credentials=True`) with env-supplied origins
and wildcard methods/headers — safe only by accident of `BACKEND_CORS_ORIGINS`
defaulting to `[]`.

## Scope decision (binding)

This is **PR #1 of the recorded 3-PR design** (§5): backend dual-mode
foundation only. Frontend migration is PR 2B; Bearer removal + SameSite=Strict
hardening is PR 2C. Invariant: **with `COOKIE_AUTH_MODE=bearer` (default),
every existing request/response is byte-identical to today** — new endpoints
exist but nothing else changes. No production flag flip in this PR.

## Functional Requirements

### FR1 — Server-side refresh sessions with rotation + reuse detection

New model `AuthSession` (table `auth_sessions`, Alembic revision on head
`v2w3x4y5z6a7`): `id`, `user_id` (FK users, indexed), `family_id` (UUID,
indexed), `token_hash` (SHA-256 of the refresh JWT's `jti`; never the raw
token), `status` (`active|rotated|revoked`), `expires_at`, `created_at`,
`last_used_at`, `replaced_by_id` (nullable self-FK). No IP/user-agent columns
(no PII creep). Register in `backend/app/models/__init__.py`.

- New refresh JWTs carry `jti` (uuid4) + `family` claims
  (`create_refresh_token` in `security.py` — keep signature
  backward-compatible; new claims optional).
- `/auth/refresh` when mode ∈ {dual, cookie} and token carries `jti`:
  look up hash atomically (`UPDATE ... WHERE status='active' RETURNING` or
  `SELECT ... FOR UPDATE`); rotate = mark `rotated`, insert successor in same
  family, return/set new pair. A `jti` found `rotated`/`revoked` = **reuse** →
  revoke every `active` session in the family + audit row
  (`auth.refresh_reuse_detected`) + 401.
- Legacy stateless refresh tokens (no `jti`, arriving via `Authorization`
  header) remain accepted while mode ∈ {bearer, dual} and keep today's
  stateless behavior — **no** session-family upgrade on header refresh
  (amended 2026-07-16 by planner: upgrading would create one family per
  refresh from pre-2B frontends — sprawl with no security gain; cookie-carried
  tokens are session-backed by construction from login/migrate). In `cookie`
  mode only session-backed tokens are accepted.
- In `bearer` mode behavior is exactly today's stateless path — no
  `auth_sessions` writes (zero-risk default).

### FR2 — Cookie issuance + dual-mode auth dependency

- `/auth/login` (and `/auth/refresh`) when mode ∈ {dual, cookie} additionally
  `Set-Cookie`: `access_token` (HttpOnly, `Secure` iff
  `settings.is_production_like`, `SameSite=Lax`, `Path=/api/v1`,
  `Max-Age` = `ACCESS_TOKEN_EXPIRE_MINUTES`), `refresh_token` (HttpOnly,
  Secure-as-above, `SameSite=Lax`, **`Path=/api/v1/auth`**, `Max-Age` = 7d).
  Response body keeps returning tokens in `bearer`/`dual` (old frontend still
  works); in `cookie` mode the body omits both tokens (returns `user` + csrf
  only). SameSite=Strict is deferred to PR 2C per recorded design.
- `deps.py::get_current_user` becomes mode-aware: `bearer` → header only
  (today's code path untouched); `dual` → cookie first, fall back to
  `Authorization: Bearer`; `cookie` → cookie only. DEV_AUTH_BYPASS branch
  unchanged (already fail-closed in prod by P0.1). WWW-Authenticate header
  retained on 401s.
- `POST /auth/logout` (new, all modes): clears both cookies with **matching
  Path/Domain/Secure/SameSite attributes**, revokes the presented session's
  family when identifiable, audits, 204. Idempotent.

### FR3 — CSRF double-submit (constant-time)

- On cookie issuance (login/refresh/migrate), also set `csrf_token` cookie
  (HttpOnly, same Secure/SameSite, `Path=/api/v1`) AND return the same value in
  the response body (`csrf_token` field) — client keeps it in memory (recorded
  design §5). Value: `secrets.token_urlsafe(32)`.
- Bootstrap for reload: extend `GET /auth/me` to rotate-or-echo the CSRF pair
  (cookie + body) when the request is cookie-authenticated, so a page refresh
  can recover the header value without re-login.
- Enforcement: for any state-changing method (POST/PUT/PATCH/DELETE) **whose
  authentication was satisfied by the access cookie**, require header
  `x-csrf-token` matching the `csrf_token` cookie via
  `secrets.compare_digest`; mismatch/absence → 403. Bearer-authenticated
  requests are exempt (headers are not CSRF-able). Exempt paths: `/auth/login`,
  `/auth/refresh` (guarded by rotation), LIFF + LINE webhook routes (own auth),
  `/auth/migrate-session` (Bearer-only by definition). Implemented once
  (middleware or shared dependency), not per-endpoint copy-paste.

### FR4 — Audited, rate-limited Bearer→cookie migration endpoint

`POST /auth/migrate-session`: accepts **only** `Authorization: Bearer`
access-token auth; mode ∈ {dual, cookie} required (404 or 409 in `bearer`
mode); issues cookie pair + new session family + csrf (same as login); writes
audit row (`auth.migrate_session`); rate-limited (reuse the sliding-window
pattern of `backend/app/core/rate_limiter.py`; 5/min per user; in-memory
per-instance is acceptable and must be noted in code comment). Does not
invalidate the presented Bearer token (dual mode tolerates both until 2C).

### FR5 — Credentialed CORS hardening (`backend/app/main.py:172-179`)

Startup guard (config validator, same style as P0.1 guards): when
`BACKEND_CORS_ORIGINS` is non-empty, reject `*` entries; middleware changes to
explicit `allow_methods`/`allow_headers` lists (include `x-csrf-token`,
`x-liff-id-token`, `authorization`, `content-type`) instead of `["*"]` —
wildcard headers/methods with `allow_credentials=True` is the exact combination
the parent plan forbids. Empty-origins behavior unchanged.

### FR6 — WebSocket ticket + Origin validation

- New table `ws_tickets` (same Alembic revision): `id`, `user_id`,
  `token_hash` (SHA-256), `expires_at` (60 s TTL), `used_at` (nullable),
  `created_at`. DB-backed because Koyeb may scale horizontally; Redis stays
  optional per repo policy.
- `POST /auth/ws-ticket` (any auth mode, any credential type): mint
  `secrets.token_urlsafe(32)`, store hash, return raw value once. Rate-limited
  like FR4.
- `ws_live_chat.py` auth: accept `{"type":"auth","payload":{"ticket":"…"}}` as
  an alternative to the existing `token` payload (JWT path stays until 2C).
  Ticket claim must be atomic single-use (`UPDATE ... WHERE used_at IS NULL
  AND expires_at > now() RETURNING`). Expired/used/unknown → `auth_error`.
- Origin validation at accept-time: when the `Origin` header is present and
  `BACKEND_CORS_ORIGINS` is non-empty, reject handshakes from origins outside
  the list (close before auth). Absent Origin (non-browser clients, tests)
  passes — document why. Never read credentials from query strings (already
  true — keep the guard comment).

### FR7 — Auth event audit (deferred here from P0.3, see designs doc §4.1)

`create_audit_log()` rows for: login success (actor id; never the password,
never token values), login failure (username masked to first 2 chars + "…",
no existence oracle in the response), refresh rotation, reuse-detection family
revocation, logout, migrate-session, ws-ticket mint. Follow the P0.3
fail-closed redaction philosophy (`settings.py::_is_secret_setting_key`
precedent): audit payloads contain identifiers and outcomes only.

### FR8 — Tests (new `backend/tests/test_cookie_auth.py` + extensions)

Monkeypatch `settings.COOKIE_AUTH_MODE` per test (idiom from
`test_liff_token.py`). Matrix — each asserts status AND cookie attributes
(HttpOnly/Path/SameSite/Max-Age) where applicable:

1. bearer mode: login/refresh/me byte-compatible with today; **no Set-Cookie
   header present**; no `auth_sessions` rows.
2. dual: login sets 3 cookies + still returns body tokens; cookie-authed GET
   works; Bearer-authed GET works; cookie wins when both present.
3. cookie: body omits tokens; Bearer-only request → 401.
4. Rotation: refresh with session-backed token issues new jti, old jti
   `rotated`; reusing old jti → 401 + whole family revoked + audit row.
5. Legacy no-jti refresh via header: accepted in dual with today's stateless
   behavior (no `auth_sessions` row created), rejected in cookie mode.
6. CSRF: cookie-authed POST without header → 403; wrong value → 403; correct →
   2xx; Bearer-authed POST without header → 2xx; login/refresh exempt.
7. Logout: cookies cleared (attribute-matched), family revoked, idempotent
   second call.
8. migrate-session: happy path, cookie-auth attempt → 401/403, rate limit
   trips (6th call in window → 429), audit row exists, bearer-mode → 409.
9. ws-ticket: mint + single-use claim, second claim fails, expired fails;
   WS auth via ticket succeeds (unit-level against the handler, matching
   existing ws test idiom); Origin rejection when configured.
10. CORS guard: `BACKEND_CORS_ORIGINS=["*"]`-equivalent config → startup
    ValueError (parametrize with P0.1 guard test idiom in
    `test_config_production_guards.py`).
11. Full backend suite: no new failures vs main baseline (record the number in
    the PR body).

## Non-Goals

- Any frontend change (`AuthContext`, `authFetch`, WS client) — PR 2B.
- Removing Bearer fallback, SameSite=Strict, flipping `COOKIE_AUTH_MODE`
  anywhere — PR 2C + human-gated ops per `migration-controls.md`.
- RBAC/permission changes (PR 2D), media signing (PR 2E).
- Cleanup job for expired `auth_sessions`/`ws_tickets` rows beyond a
  best-effort batched delete piggybacked on ticket mint/refresh (a dedicated
  retention job belongs with P1.6 scheduler-leadership work — record as
  follow-up, do not build a scheduler here).
- Redis-backed rate limiting or distributed limiter.
