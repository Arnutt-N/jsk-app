## Problem Statement

1. **D1 — Live-chat shows every operator the same LINE-ID masking.** Staff conversation
   surfaces render `maskLineUserId()` unconditionally, while the R3-M7 server policy
   (`pii_masking`: full IDs for SUPER_ADMIN/ADMIN, masked for the rest) already applies
   to users/exports. Result: admins lose the full ID they are entitled to in live-chat,
   and masking policy is inconsistent between pages. (Masking the API's `line_user_id`
   key itself is NOT the fix — see decision 1.)
2. **D2 — Postback replies bypass the outbox.** `handle_postback_event` sends the CSAT
   thank-you (and status replies flow without a box) *before* the per-event commit, so a
   commit failure after the send leaves a ghost: the citizen is thanked for a score that
   was never recorded. R3-M3 fixed this for message events only.
3. **D3 — The 50MB media cap guards disk, not RAM.** `download_message_content` fully
   materializes the LINE body via the SDK before `persist_line_media` measures it, so one
   large video (or several concurrent downloads) can spike worker memory despite the cap.
4. **D4 — request-v2 submits with no JS validation gate.** The third LIFF form relies on
   HTML `required` only, so whitespace-only values submit; worse, it posts the phone as
   `phone` while the backend reads `phone_number`, so request-v2 phone numbers are
   silently dropped server-side.

## Solution

1. Live-chat display masking becomes role-aware (same rule as `pii_masking`); the raw API
   key stays untouched for functional use and is documented as such.
2. The webhook postback branch uses the outbox like the message branch; the CSAT
   thank-you is queued and drained after commit.
3. Media download streams with a pre-check + running cap: oversized bodies never fully
   land in RAM; the persist skip path and return contract stay unchanged.
4. request-v2 gains the twin pages' trim-aware `validateForm` + inline errors + submit
   gate, and maps `phone` → `phone_number` in the payload.

## User Stories

1. As an ADMIN, I want to see the full customer LINE ID in live-chat, so that I can contact or reference the exact account.
2. As an AGENT, I want customer LINE IDs masked in live-chat, so that I handle only the data my role needs — without any chat action breaking.
3. As a citizen tapping LINE buttons, I want my status/CSAT reply to reflect recorded data only, so that I never get a thank-you for a lost score.
4. As an operator, I want oversized LINE media skipped cheaply, so that one big video cannot destabilize the backend.
5. As a citizen on the request-v2 form, I want clear inline errors and no lost phone number, so that my request arrives complete.

## Implementation Decisions

1. **D1 display-layer, not API-layer.** Research proved the API `line_user_id` is a
   functional key: 13 routes take `{line_user_id}` (`admin_live_chat.py`), WS rooms and
   ~30 frontend call sites key off it. Masking it per role would 403 every non-admin
   action. So: new `maskLineUserIdForRole(id, role)` in `frontend/lib/mask.ts`
   (full for SUPER_ADMIN/ADMIN per `useAuth().user.role`, masked otherwise), applied at
   every live-chat render point after an audit; raw key kept + documented.
2. **D2 mirrors R3-M3 exactly.** `webhook.py` postback branch creates/passes `box` like
   the message branch; `handle_postback_event`/`handle_csat_response` gain
   `outbox: Outbox | None = None`; `handle_check_status` already accepts it — pass
   through. `show_loading_animation` stays a direct call (ephemeral, not persisted data).
3. **D3 streams over raw httpx, outside the SDK blob method.** The SDK's
   `_preload_content=False` path is BROKEN in the installed version (gate r1 proof:
   `__call_api` calls `getheaders()`/`.data`, absent on aiohttp `ClientResponse` →
   AttributeError swallowed into `(b"", None)` — silent total outage). So: httpx
   `stream()` to the SDK-pinned host + path with the channel token, `Content-Length`
   pre-check + running cap, `_MediaTooLarge` → existing skip shape. Preview branch
   stays on the SDK preloaded call (small by nature, proven path).
4. **D4 mirrors the single page.** `validateForm` (trim-aware + phone 9–10 + required
   selects), `fieldErrors` state, red-border UI, submit gate — plus one-line payload map
   `phone_number: formData.phone`. Backend `_require_content` (topic/description,
   whitespace-aware) stays the data backstop; names stay UX-level (anonymous tips are
   valid by design).

## Testing Decisions

- D1: helper unit tests (role × value matrix) + audit-driven component test (admin sees
  full / agent sees masked / action keys unchanged); zero raw renders asserted by audit.
- D2: mirror `test_webhook_outbox.py` fakes (`process_webhook_events` + FakeSession):
  postback drains after commit; CSAT thank-you queued not sent; invalid data queues nothing.
- D3: drive the real helper against `httpx.MockTransport` (mocking
  `download_message_content` would bypass the new code): over-cap length never reads;
  lying length aborts mid-stream; normal body returns bytes; `(b"", None)` shape preserved.
- D4: new `request-v2/__tests__/validation.test.tsx` mirroring the twin files:
  whitespace rejection, over-long phone rejection, valid submit asserts payload
  contains `phone_number` and no `phone`.
- Naming: tests name the user-visible behavior, not internals.

## Out of Scope

- Opaque `conversation_key` migration for live-chat (the alternative to D1's approach;
  rejected: 13 routes + WS rooms + ~30 frontend sites for no user-visible gain now).
- API-layer masking of the live-chat `line_user_id` key (breaks function; see decision 1).
- `phone` → `phone_number` mapping on service-request-single (same one-line shape as D4;
  separate PR to bound blast radius — filed as follow-up).
- Preview-branch streaming (previews are small; preloaded path stays).
- Follow-button outbox (follow/unfollow send nothing user-visible today).
- Permission-matrix or `pii_masking` policy changes.
