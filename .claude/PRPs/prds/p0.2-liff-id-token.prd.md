## Problem (verified in `docs/remediation/preflight-evidence-and-designs.md` §1)

All three form-submitting LIFF pages send client-supplied `liff.getProfile().userId`
as `line_user_id` in the body and never send an ID token; the backend trusts that
value unverified (`details.source = "LIFF-unverified"`). Anyone can submit service
requests impersonating any LINE user. `LIFF_STRICT_MODE` exists in config (PR 0A)
but is wired to nothing.

## Scope decision (binding)

The parent plan's end state ("header mandatory, remove LIFF-unverified fallback")
is NOT this PR. Per the consolidated review's CRITICAL finding, enforcement must be
flag-gated to avoid breaking production while old clients are live. This PR ships:
- **P0.2a:** all three LIFF pages transmit the ID token.
- **P0.2b:** backend reads `LIFF_STRICT_MODE`; **default OFF** (transition mode).
Fallback removal happens in a later PR after the `migration-controls.md` gate passes
(token presence 100% for 3-5 days, etc.).

## Functional Requirements

### FR1 — Frontend token transmission (3 pages)

Files: `frontend/app/liff/service-request/page.tsx`,
`frontend/app/liff/request-v2/page.tsx`,
`frontend/app/liff/service-request-single/page.tsx`.

- After successful `liff.init(...)` (and login check where the page does one),
  capture `liff.getIDToken()` into state alongside the existing profile capture.
  Handle `null` (LIFF opened outside LINE / not logged in) without breaking flow.
- On submit, add header `"x-liff-id-token": token` to the
  `POST /api/v1/liff/service-requests` fetch ONLY when the token is non-null.
  Keep the existing body `line_user_id` behavior untouched (transition
  compatibility; body value becomes advisory once a token is present because the
  backend already prefers the verified sub).
- On a 401 response from submit, surface the page's existing error UI with a clear
  Thai message telling the user to close and reopen the form in LINE
  (token expired/invalid case). Follow each page's existing error-handling pattern.
- Match each page's existing style (`liff` import vs `window.liff` — pages differ;
  keep each page's own idiom).

### FR2 — Backend `LIFF_STRICT_MODE` wiring (`backend/app/api/v1/endpoints/liff.py`)

In `create_service_request`:
- Token present → verify (existing `verify_liff_token`), owner = verified `sub`,
  `source = "LIFF v2"` (unchanged). A body `line_user_id` differing from the
  verified sub must be logged (`logger.warning` with the verified sub in masked
  form only — e.g. first 6 chars + "…"; never log the full IDs or the token) and
  ignored.
- Token absent + `LIFF_STRICT_MODE` **true** → `HTTPException(401,
  "LIFF ID token required")`. No DB write.
- Token absent + flag **false** (default) → current fallback (body `line_user_id`,
  `source = "LIFF-unverified"`) + `logger.warning("LIFF_token_missing_transition_mode")`
  so the rollout gate's "token-presence 100%" signal is measurable from logs.
- No schema change to `service_request_liff.py` (body `line_user_id` stays accepted
  for transition; document why in the PR body).

### FR3 — Tests: new `backend/tests/test_liff_token.py`

Use `test_client` fixture (services are up in this sandbox) + monkeypatch. Mock
LINE's verify endpoint by monkeypatching `httpx.AsyncClient` (repo idiom from
`test_rich_menu_alias_service.py`) OR monkeypatch `verify_liff_token` where the
HTTP layer isn't the subject — but at least one test must exercise the real
`verify_liff_token` parsing path (200 with sub / 200 without sub / non-200).
Toggle the flag via `monkeypatch.setattr(settings, "LIFF_STRICT_MODE", ...)`.

Matrix (each asserts status code AND, for 201s, the persisted
`line_user_id`/`details.source`):
1. flag OFF, no token → 201, owner = body value, source `LIFF-unverified`.
2. flag OFF, valid token, forged body `line_user_id` → 201, owner = verified sub
   (forgery ignored), source `LIFF v2`.
3. flag OFF, invalid token (LINE 400) → 401 (present-but-bad is rejected even in
   transition mode — matches current behavior).
4. flag ON, no token → 401, and no ServiceRequest row created.
5. flag ON, valid token → 201, owner = sub.
6. flag ON, invalid token → 401.
7. verify_liff_token: LINE 200 without `sub` → 401.
8. Empty LINE_LOGIN_CHANNEL_ID → 503 is already covered in
   test_config_production_guards.py; do not duplicate.

### FR4 — Docs

`docs/remediation/migration-controls.md`: in the `LIFF_STRICT_MODE` row/section,
note the wiring now exists (backend enforces when true; transition logging line
`LIFF_token_missing_transition_mode` is the token-presence signal) — keep the
enable-threshold text unchanged.

## Non-Goals

- Removing the unverified fallback or making the header mandatory (later PR, gated).
- Flipping `LIFF_STRICT_MODE` anywhere (prod config change = human decision).
- Any change to media upload or location endpoints used by the LIFF pages.
- Frontend unit tests for the pages (no page-level test harness exists for LIFF
  pages today; CI covers lint/tsc/build + Playwright smoke).

## Rollout note (PR body)

Ship with `LIFF_STRICT_MODE=false` (default — no env change needed). Frontend
deploys via Vercel on merge; backend via Koyeb CD. Safe in any deploy order because
the flag is off: new frontend + old backend = header ignored; old frontend + new
backend = fallback path. Enabling strict mode later follows the
`migration-controls.md` gate (token presence 100% for 3-5 consecutive days measured
via the `LIFF_token_missing_transition_mode` log line).
