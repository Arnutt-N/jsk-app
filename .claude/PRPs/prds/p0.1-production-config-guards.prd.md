## Problem

Production can currently start with unsafe combinations, all verified against live
source on 2026-07-15:

1. `DEV_AUTH_BYPASS=true` in production silently enables a full admin auth bypass —
   `backend/app/api/deps.py:31-47` returns a mock ADMIN user when no token is sent.
   Nothing rejects the flag in production (`backend/app/core/config.py:19`).
2. `SECRET_KEY` has no strength requirement — the env-example placeholder
   `change_this_to_a_secure_random_string` (or any short string) is accepted and
   silently signs all JWTs.
3. `LINE_LOGIN_CHANNEL_ID` defaults to `""`; LIFF verification then posts an empty
   `client_id` to LINE (`backend/app/api/v1/endpoints/liff.py:25`) and fails as a
   confusing generic verification error instead of a clear config error.
4. `ENCRYPTION_KEY` is already fail-closed in production via
   `credential_service.validate_configuration()` called from the lifespan
   (`backend/app/main.py:125`) — but there is no production-combination test
   coverage locking that behavior.

P0.1 acceptance criteria (parent plan): unsafe production combinations fail during
configuration/startup; safe development defaults remain usable; logs do not reveal
secret values; startup, credential, and auth-gate tests pass.

## Goals (Functional Requirements)

### FR1 — Production guard validator in `backend/app/core/config.py`

Add a pydantic `@model_validator(mode="after")` that, ONLY when
`ENVIRONMENT.strip().lower() == "production"`, rejects settings load when any of:

1. `DEV_AUTH_BYPASS` is true.
2. `SECRET_KEY` shorter than 32 characters OR equal (case-insensitive) to a known
   placeholder — at minimum `change_this_to_a_secure_random_string` (the string in
   both env examples); include obvious variants (`changeme`, `secret`, empty).
3. `LINE_LOGIN_CHANNEL_ID` empty/whitespace.
4. `ENCRYPTION_KEY` empty/whitespace (full Fernet-validity check stays in
   `credential_service` — see FR3).

Requirements:
- Collect ALL violations and raise one `ValueError` listing every failed control by
  NAME with a one-line remedy each — never echoing the configured value.
- Development/test behavior unchanged: guards must not run outside production
  (existing conftest env uses `ENVIRONMENT=development`, `SECRET_KEY=pytest-secret-key`
  — 17 chars — and must keep passing).

### FR2 — Fail-closed LIFF verification in `backend/app/api/v1/endpoints/liff.py`

`verify_liff_token()` must check `settings.LINE_LOGIN_CHANNEL_ID` BEFORE calling
LINE: if empty → log an explicit config error and raise HTTP 503
("LIFF verification unavailable: server misconfiguration") without any outbound
call. (FR1 makes this unreachable in production; this protects development and any
future env drift.)

### FR3 — `ENCRYPTION_KEY` production coverage (no behavior change)

`credential_service.validate_configuration()` already rejects missing/invalid keys
in production. Do NOT duplicate Fernet parsing in config.py. Add the missing tests
(FR4) to lock the behavior.

### FR4 — Tests: new `backend/tests/test_config_production_guards.py`

Mirror the style of `backend/tests/test_config_migration_controls.py`
(`build_settings(_env_file=None, **overrides)` — no DB needed). Cover at minimum:
- production + each single violation → `ValidationError` (bypass on / short key /
  placeholder key / empty channel id / empty encryption key).
- production + all-safe values → loads.
- multiple violations → error message names ALL failed controls.
- error message does NOT contain the offending secret value.
- development defaults (bypass off, short key, empty channel id) → loads (guards
  inactive outside production).
- `credential_service.validate_configuration()`: production + empty key raises;
  production + valid Fernet key passes; development + empty key warns-but-passes
  (monkeypatch settings; mirror existing service-test patterns if any).
- `verify_liff_token` with empty `LINE_LOGIN_CHANNEL_ID` raises HTTP 503 without
  network I/O (monkeypatch httpx.AsyncClient to fail the test if instantiated).

### FR5 — Docs

- `backend/.env.production.example`: comment each guarded var with its production
  requirement (≥32-char SECRET_KEY, required LINE_LOGIN_CHANNEL_ID / ENCRYPTION_KEY,
  DEV_AUTH_BYPASS must stay false/absent).
- `docs/remediation/migration-controls.md`: append a short "P0.1 production
  startup guards" section listing the enforced controls and the pre-deploy
  checklist (operator must verify real prod env values on Koyeb BEFORE deploying —
  a weak/missing value that previously started silently will now fail startup,
  which is the intent but must not be a surprise outage).

## Rollout note (goes in PR body)

Before deploying to Koyeb prod: confirm `SECRET_KEY` (≥32 chars, non-placeholder),
`LINE_LOGIN_CHANNEL_ID`, `ENCRYPTION_KEY` are set to real values and

will (correctly) refuse to start.
