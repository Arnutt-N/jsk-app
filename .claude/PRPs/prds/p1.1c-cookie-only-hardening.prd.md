## Problem (verified in current backend code)

PR 2A dark-shipped the cookie foundation behind `COOKIE_AUTH_MODE=bearer`
(default, zero behavior change). After the dual-mode rollout observation
window passes (login/refresh success + zero `auth.refresh_reuse_detected`
audit rows for 3-5 days per `migration-controls.md`), three residual
hardening gaps remain open and intentionally deferred from PR 2A/2B:

1. **Bearer fallback keeps an XSS exfil channel open.** `deps.py:55-62`
   still resolves `Authorization: Bearer` when `COOKIE_AUTH_MODE != "cookie"`
   and no cookie is present. With `COOKIE_AUTH_MODE=cookie` the header path
   is already dead, but `dual` mode keeps it live so an un-migrated frontend
   keeps working. Once PR 2B is live and observation passes, dual mode is
   pure attack surface — Bearer is no longer the *fallback for an un-migrated
   client*, it is the *path an XSS uses to skip the HttpOnly cookie jar*.
2. **`SameSite=Lax` lets cross-site navigations send the access cookie.**
   `cookie_auth.py:28` ships `COOKIE_SAMESITE = "lax"` with the explicit
   comment "SameSite is `Lax` here; `Strict` is deferred to PR 2C per the
   recorded design". `Lax` is the safe default for the dark rollout because
   it allows top-level navigations (a clicked admin link from another site
   still authenticates). With cookie-only enforced, top-level navigation
   into the admin app is not a real use case (admin is opened directly by
   operators, not via inbound links), so `Strict` closes the cross-site
   GET-with-credentials vector that `Lax` keeps open.
3. **`COOKIE_AUTH_MODE=dual` keeps the response body leaking tokens.**
   `auth.py:191,321,471` returns access/refresh tokens in the JSON body
   whenever mode is `dual` (so an un-migrated frontend keeps working).
   The body copy is the reason `dual` exists; once cookie-only is
   enforced the body copy is a second exfil channel — any XSS that can
   read `await fetch('/auth/login').then(r => r.json())` gets the raw
   access + refresh tokens, defeating the entire point of HttpOnly cookies.

## Scope decision (binding)

This is **PR #3 of the recorded 3-PR design** (§5 of the preflight designs
doc): the *hardening* tail. It removes Bearer fallback, tightens
SameSite to `Strict`, removes token body copies, and removes the
`COOKIE_AUTH_MODE` knob + the `NEXT_PUBLIC_COOKIE_AUTH` flag — once 2C
ships, cookie auth is the only auth and the dual/bearer modes exist only
as a documented rollback path (redeploy previous image).

**Invariant:** PR 2C code, deployed with the old env (`COOKIE_AUTH_MODE=
dual`, `NEXT_PUBLIC_COOKIE_AUTH=true`), MUST keep working during the
overlap window where the backend is on 2C but the frontend is not yet
rebuilt on 2C. This is the same "ships dark behind the flag" principle
PR 2A/2B used — the new hardening only takes effect when the matching
env config is flipped to its terminal value.

## Functional Requirements

### FR1 — Remove Bearer fallback in `get_current_user`

`backend/app/api/deps.py:26-153`: `get_current_user` becomes
cookie-only. Concretely:
- Drop the `COOKIE_AUTH_MODE in ("dual","cookie")` branch condition:
  the cookie resolution path runs unconditionally.
- Drop the `if token is None and settings.COOKIE_AUTH_MODE != "cookie":`
  Bearer fallback block (`deps.py:60-62`).
- The `token_source` state still records `"cookie"` vs `None` so CSRF
  enforcement (`deps.py:146-153`) keeps working unchanged — only
  cookie-sourced auth is CSRF-checked; with Bearer gone every authed
  request is cookie-sourced, so every mutating request is CSRF-checked
  (the intended end state).
- `DEV_AUTH_BYPASS` branch (`deps.py:71-86`) is unchanged — it only
  fires when no cookie is present AND `DEV_AUTH_BYPASS=true` is
  explicitly set. In prod this is fail-closed by P0.1
  (`is_production_like` blocks the env var).
- `WWW-Authenticate: Bearer` header on 401s is removed (the only auth
  scheme now is cookies; advertising Bearer is misleading). Replaced
  with no `WWW-Authenticate` header (401 body keeps the message).

### FR2 — Tighten SameSite from `Lax` to `Strict`

`backend/app/core/cookie_auth.py:28`:
`COOKIE_SAMESITE = "lax"` → `COOKIE_SAMESITE = "strict"`.

This applies to all three cookies (access, refresh, csrf) on both `set`
and `delete` paths (`set_auth_cookies` / `clear_auth_cookies`) because
both use `_cookie_kwargs` / pass `samesite=` through the same constant.

**Acceptance implication:** a top-level navigation from another site
into the admin app will NOT carry the access cookie — the user will land
unauthenticated and be redirected to `/login`. This is intentional: the
admin app is not an inbound-link destination. Operators navigate
directly to the admin URL.

**Rollout gotcha (record in PR body + `migration-controls.md`):**
the `Strict` flip means every operator with an existing `Lax` cookie
keeps using it until it expires (access: `ACCESS_TOKEN_EXPIRE_MINUTES`,
refresh: 7d). The new `Strict` attribute only takes effect when the
cookie is (re)set by the next login/refresh. No migration job needed —
refresh naturally rotates the access cookie within minutes, refresh
rotates the 7d cookie on first rotation. Document a "first-refresh
after-deploy" expectation in the rollout runbook so operators don't
report a "stuck logged out" ticket when their browser keeps an old
`Lax` cookie across the deploy boundary.

### FR3 — Remove token body copies in `dual` mode

`backend/app/api/v1/endpoints/auth.py:186-191,228-233,321,471`: every
site that branches on `COOKIE_AUTH_MODE == "cookie"` to decide whether
to omit tokens from the response body is changed to always omit tokens
from the body. Concretely:
- `/auth/login` (`auth.py:186-191`): always `set_auth_cookies`, body
  returns `{user, csrf_token}` (no `access_token` / `refresh_token`).
- `/auth/refresh` (`auth.py:228-233,321`): always set cookies, body
  returns `{user, csrf_token}`.
- `/auth/me` (`auth.py:471`): `body_omitted` is always `True`; body
  returns `{user, csrf_token}`.
- The `if refresh_token is None and settings.COOKIE_AUTH_MODE != "cookie":`
  guard at `auth.py:233` is removed — refresh is always cookie-carried
  now, a missing refresh cookie is always a 401.

**Bearer acceptance:** a request that sends `Authorization: Bearer`
to `/auth/login` is now meaningless (the response sets cookies and the
body has no tokens). The endpoint does not *reject* the header — it
just ignores it. Document this in the rollout note: any non-browser
client (e.g. a CI script using Bearer) must switch to cookie-jar
handling (`requests.Session()` / `curl -c/-b`).

### FR4 — Remove `COOKIE_AUTH_MODE` knob

`backend/app/core/config.py:40`:
`COOKIE_AUTH_MODE: Literal["bearer", "dual", "cookie"] = "bearer"` is
**removed**. The three modes collapse to one (cookie-only).

- Remove the `Literal["bearer", "dual", "cookie"]` type — the field
  goes away entirely.
- `backend/tests/test_config_migration_controls.py:21,26,28,39` — the
  two existing tests (`test_cookie_auth_mode_defaults_to_bearer` and
  the parametrized `test_cookie_auth_mode_accepts_*`) are deleted.
  The `test_unknown_cookie_auth_mode_rejected` parametrize entry
  (`Line 39: ("COOKIE_AUTH_MODE", "unknown")`) is removed because the
  field no longer exists to reject a value for.
- The startup guard logic (if any was added in 2A to validate the
  literal) is removed alongside the field.
- **Backward-compat:** if a deployed env still sets `COOKIE_AUTH_MODE`
  (e.g. an un-pruned Koyeb env var), the Pydantic settings loader will
  ignore unknown env vars (extra="ignore" or equivalent) — verify this
  is the settings model behavior; if it is `extra="forbid"`, add an
  `env_ignore` or accept-and-warn path. Record the verified behavior
  in the PR body so ops knows the stale env var is harmless.
- `docs/remediation/migration-controls.md`: the entire `COOKIE_AUTH_MODE`
  section is rewritten to "Removed in PR 2C — cookie auth is the only
  mode; the env var is ignored if still set." with a pointer to the
  rollback procedure (redeploy PR 2B image, set `COOKIE_AUTH_MODE=dual`).

### FR5 — Remove frontend `NEXT_PUBLIC_COOKIE_AUTH` flag

`frontend/lib/authFetch.ts` and every consumer of `COOKIE_AUTH`:
the flag-gated branch is removed — the cookie path becomes the only
path. Concretely:
- `authFetch.ts`: the module-top `const COOKIE_AUTH = process.env
  .NEXT_PUBLIC_COOKIE_AUTH === 'true'` constant is removed; the cookie
  branch (`credentials: 'include'`, CSRF attachment, no-Bearer) becomes
  the unconditional behavior.
- `contexts/AuthContext.tsx`: the flag-conditional migration/bootstrap
  branches collapse to the cookie-only path (state machine, `/auth/me`
  bootstrap, single-flight refresh, one-time Bearer→cookie migration,
  ticket-based WS).
- `hooks/useWebSocket.ts`: the JWT-as-first-message path (preserved by
  PR 2B for flag-off regression) is removed — ticket auth is the only
  WS auth.
- Any `NEXT_PUBLIC_COOKIE_AUTH` env references in `.env.example`,
  Vercel project settings, or docs are removed.

> **Note:** this PR is *backend + frontend*. PR 2A was backend-only,
> PR 2B was frontend-only. PR 2C removes the *flags* that both PRs
> gated their behavior behind, so it touches both layers. The two
> deploys can still be ordered (backend first, then frontend rebuild)
> because the FR1-FR4 hardening is dark behind the still-`dual` env
> until ops flips to cookie-only — see Rollout note.

### FR6 — Tests (extend `test_cookie_auth.py` + frontend vitest)

Backend (`backend/tests/test_cookie_auth.py` is the existing 2A file):
1. **Cookie-only is the only mode:** remove the `bearer`/`dual`
   monkeypatch from every existing test — they all run in the now-only
   mode. The mode matrix tests (tests 1-3 in 2A FR8) collapse to
   single-mode assertions.
2. **Bearer header is ignored:** `GET /api/v1/admin/...` with
   `Authorization: Bearer <valid_jwt>` and no cookies → 401 (today's
   dual-mode test would have returned 200). This proves Bearer
   fallback is gone.
3. **SameSite=Strict on set:** introspect `Set-Cookie` header for

   `SameSite=Lax` in 2A test 2).

5. **Body omits tokens always:** `/auth/login`, `/auth/refresh`,

6. **CSRF enforced on every mutating request:** POST/PUT/PATCH/DELETE

7. **WS ticket-only:** `authenticate_ws_user` (JWT path) is removed

8. **Config guard gone:** `test_config_migration_controls.py` no

9. **Full backend suite:** no new failures vs main baseline (record
   count in PR body). The 2A file shrinks because the mode matrix
   collapses.

Frontend (`frontend/contexts/AuthContext.tsx` vitest, extended from

10. **Flag-off regression test removed:** the 2B test 10 ("flag off =
    byte-identical to today") is deleted — there is no flag-off path.
11. **Cookie path is the only path:** all existing 2B tests run

12. **No `Authorization: Bearer` injection anywhere:** grep-proof the

13. **WS client sends ticket only:** `useWebSocket` test asserts the

  Untouched.

  service-to-service Bearer usage; if one is discovered during
  implementation it is filed as a follow-up, not added here.
- **Cookie retention / cleanup job** — still P1.6 (the opportunistic
  delete piggybacked on ticket mint/refresh from 2A is the interim
  fix; a dedicated scheduler-leadership job belongs with P1.6).
- **Removing the legacy `auth_sessions` / `ws_tickets` tables** —
  these are the *session backing store*, not legacy; they stay.
- **Rolling back the dual-mode rollout itself** — out of scope; the
  rollback path is "redeploy PR 2B image" (documented, not coded).
- **Redis-backed rate limiting** — closed in PR #140 (already prod).

## Rollout note (PR body)

Ships dark behind the still-`dual` env: with `COOKIE_AUTH_MODE=dual`
left on prod, FR1-FR4 hardening is dormant — Bearer fallback is
already live in `dual`, `SameSite=Lax` is already in effect, body
tokens are already returned. The new code only takes effect when ops
flips to `cookie`-only (the terminal state).

**Deploy order is frontend-first (the OPPOSITE of 2A).** 2C is a
strict *subset* of 2B behavior — it *removes* a path (the Bearer
fallback in FR1 is removed unconditionally, not gated on
`COOKIE_AUTH_MODE`). A 2C backend deployed before the 2C frontend
would reject every 2B frontend's `Authorization: Bearer` requests and
log all operators out. 2A was backend-first because 2A was a strict
*superset* (it added a path); 2C is the inverse case. This is the
single most important operational gotcha in this PR — record it in
`migration-controls.md` and in the PR body in BOLD.

Rollout sequence:

1. **Deploy frontend PR 2C rebuild FIRST** (cookie-only client, sends
   no `Authorization: Bearer` — the 2B backend tolerates it because
   `dual` accepts cookies). Verify admin login works against the
   still-2B backend.
2. **Deploy backend PR 2C** (cookie-only server). The 2C frontend is
   already sending cookies-only, so it keeps working. Verify
   `/health` 200 + admin login.
3. **Ops: flip backend env `COOKIE_AUTH_MODE` from `dual` to `cookie`**
   (or unset it — the field is gone, the var is ignored either way;
   document the chosen option in `migration-controls.md`). Redeploy
   backend. This is the moment FR1-FR4 take effect.
4. **Verify on prod:**
   - Browser DevTools: `SameSite=Strict` on the three cookies after a
     fresh login.
   - `curl -H "Authorization: Bearer <jwt>" https://.../api/v1/admin/...`
     returns 401 (Bearer is dead).
   - `/auth/login` body has no `access_token` key.
   - Audit log: zero `auth.refresh_reuse_detected` rows over 24h.
5. **Observe 3-5 days** (login/refresh success rate, no reuse alerts,
   no "stuck logged out" operator tickets). If any indicator regresses:
   - **Rollback step 3** → redeploy 2B backend image with
     `COOKIE_AUTH_MODE=dual`. The frontend 2C rebuild keeps working
     because `dual` tolerates a cookie-only client. Operators' old
     `Lax` cookies come back into scope on the next login.
6. **After observation:** file a follow-up to prune the stale
   `COOKIE_AUTH_MODE` env var from Koyeb + the stale
   `NEXT_PUBLIC_COOKIE_AUTH` from Vercel (cosmetic; they're ignored).
