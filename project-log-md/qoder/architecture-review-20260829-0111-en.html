Deepening candidates — 8 ข้อ

1. ServiceRequest — endpoint ที่กลายเป็น service เสียเอง

Strong

Files: backend/app/api/v1/endpoints/admin_requests.py (720), app/core/request_workflow.py, app/core/permissions.py

Problem: ไม่มี request_service — endpoint คือ service: มี db.execute/select ตรง ๆ ~30 จุด, 6 Pydantic models นิยามในไฟล์, 4 stats queries, และ private helpers (_check_workflow_guards:370, _apply_status_and_assignment:436) ที่รับของ 3 ระดับพร้อมกัน (Pydantic + ORM + User) กฎ state machine กระจายอยู่ 3 ที่: request_workflow.py (transition map) + permissions.py (สิทธิ์) + ตัว endpoint (enforce) — แก้หนึ่งการเปลี่ยนสถานะต้องแตะสามไฟล์ Deletion test: ลบ private helpers แล้วตรรกะไปเกิดซ้ำในทุก route — มันทำงานอยู่จริง แต่อยู่ผิดที่

Solution: สร้าง ServiceRequestService ที่รับ plain data แล้วคืนผลลัพธ์: โอนย้าย queries, การเปลี่ยนสถานะตาม workflow, และ audit writes เข้าไป; endpoint เหลือแค่ auth + เรียก + แปลง response

Benefits: Locality — state machine ทั้งเส้นอยู่ในไฟล์เดียว ทดสอบได้โดยไม่ต้องตั้ง HTTP; Leverage — stats queries ทั้ง 4 ชุดเรียกใช้ซ้ำจากที่อื่นได้; interface กลายเป็น test surface ตรง ๆ

BEFORE — workflow กระจาย 3 ที่, ตรรกะฝังใน endpoint

admin_requests.py — interface ใหญ่: ~30 จุดแตะ DB + 6 schemas + 4 private helpers
บาง: ไม่มีอะไรซ่อน — ทุกอย่างโผล่ที่ผิว
request_workflow.py+permissions.py+endpoint helpers

AFTER — module เดียวลึก, endpoint บาง

ServiceRequestService
interface เล็ก: โหลด/เปลี่ยน/สถิติ
ลึก: queries + state machine + permissions + audit ฝังข้างใน

2. HTTP concern รั่วเข้า live-chat service (seam ที่ทำค้าง)

Strong

Files: backend/app/services/live_chat_service/sessions.py (raise HTTPException 7 จุด: บรรทัด 41, 61, 84, 119, 124, 158, 191), endpoints/admin_live_chat.py:264–281

Problem: การแยก live_chat_service/ เป็น 10 โมดูล (จาก PR #137) ย้ายโค้ดสำเร็จแต่ย้าย HTTP concern ออกไม่หมด: ตัวบริการยังเลือก status code เอง แล้ว endpoint ก็จับ ValueError เทียบ ค่าสตริง เพื่อ map กลับเป็น status อีกรอบ — สองชั้นทำหน้าเดียวกัน

Solution: บริการ raise domain exceptions (SessionAlreadyClaimed, NotSessionOperator) — ไม่มี from fastapi import ใน service; endpoint มีที่แปลค่าเป็น HTTP เพียงจุดเดียว

Benefits: ทดสอบพฤติกรรมของ session lifecycle ผ่าน interface ของมันได้โดยไม่ต้องพึ่ง FastAPI; การแก้ข้อความ/รหัสสถานะทำที่เดียว — locality; seam ระหว่าง domain กับ transport ชัดขึ้นทั้ง 10 โมดูลใน package

BEFORE — HTTP แปลสองรอบ

service: raise HTTPException(409)
endpoint: catch ValueError
  → เทียบสตริง → status ใหม่

AFTER — domain exception แปลรอบเดียว

service: raise SessionAlreadyClaimed
endpoint: handler map ทีเดียว → 409

3. HTTP module หนึ่งเดียว — ปิดงานค้างของ apiFetch

Strong

Files: frontend/lib/api-error.ts (apiFetch), frontend/hooks/useApiFetch.ts (45), frontend/lib/authFetch.ts, 40+ ไฟล์เรียก fetch() ตรง, ~25 หน้าประกาศ const API_BASE = '/api/v1' เอง

Problem: apiFetch มีอยู่แต่ถูก adopt แค่ ~3 ไฟล์; อีก 40+ ไฟล์เรียก fetch() ดิบ ๆ — ได้ cookies/CSRF จาก interceptor ของ authFetch.ts แต่ไม่ได้การอ่าน error, ข้อความไทยตามสถานะ, หรือ logging แบบเดียวกัน ความไม่สม่ำเสมอนี้มองไม่เห็นตอนรัน แต่จริง Deletion test กับ useApiFetch: interface (data/loading/error/execute/clearError) ใหญ่พอ ๆ กับตัวมันเอง = ตื้น

8. user_identity_service — seam ตื้น + flag ที่ตายแล้ว

Speculative

Files: backend/app/services/user_identity_service.py (175), backend/app/core/config.py:58, callers 5+ ไฟล์

Problem: helpers สาธารณะ 4 ตัว (resolve_by_line_id, child_filter, populate_surrogate, decrypt_user_line_id) ตัวละ 3–8 บรรทัด — คนเรียกต้องจำเองว่าเมื่อไหร่เรียกตัวไหน และใครถือ commit; ความซับซ้อนจริง (เลือก HMAC key, บรรทัด 33–45) เป็นส่วนตัวหมด; และ LINE_ID_STORAGE_MODE ยังเป็น Literal["plaintext","dual","pseudonym"] ทั้งที่หลัง PR #199 เหลือสถานะเดียวที่ใช้ได้ — ประเภทประกาศ 3 สถานะ เอกสารบอกมี 1

Solution: พับเป็น value object UserIdentity (.from_raw() / .resolve() / .for_storage()) ที่ซ่อนการเลือก key และความเป็นเจ้าของการบันทึก; ยุบ LINE_ID_STORAGE_MODE เป็นค่าคงที่

Benefits: pseudonym contract อยู่หลัง interface เดียวที่เทสต์ได้; ลด "ข้อควรรู้" ที่คนเรียกต้องจำ — interface คือ test surface; เสี่ยงต่ำเพราะเป็นงานหด ไม่ใช่ย้าย

resolve · child_filter · populate · decrypt + โหมด 3 ค่า

Top recommendation — เริ่มที่ข้อ 3: HTTP module หนึ่งเดียว

ข้อ 3 (adminApi / liffApi) คือจุดเริ่มที่ดีที่สุด เพราะเป็น leverage สูงสุดต่อความเสี่ยงต่ำสุด: 40+ จุดเรียกใช้ดีขึ้นพร้อมกันโดยไม่ต้องเปลี่ยนพฤติกรรมของใคร, มันเป็นการปิดงานที่เริ่มไว้แล้ว (apiFetch + authFetch) แทนที่จะประดิษฐ์สิ่งใหม่, และมันปลดล็อกการเทสต์ของทุกหน้าพร้อมกัน — พังงาเดียวที่ดึงเรือทั้งลำ

ลำดับที่แนะนำ: ข้อ 3 → ข้อ 4 (liffApi ได้ใช้ทันที) → ข้อ 2 (งานเล็ก เห็นผลเร็วฝั่ง backend) แล้วค่อยข้อ 1 และ 6 ซึ่งเป็นงานลึกแต่ขอบเขตกว้างกว่า ข้อ 5, 7, 8 เก็บไว้ทำเมื่อแตะพื้นที่นั้นอยู่แล้ว
