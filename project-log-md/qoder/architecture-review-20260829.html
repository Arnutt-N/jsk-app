2026-08-29 · โอกาสทำโมดูลให้ลึกขึ้น ครอบคลุมทั้งฝั่ง backend (FastAPI) และ frontend (Next.js)

ภาพรวม: ฝั่ง service layer ของโปรเจกต์ทำได้ดี (booking, broadcast, live-chat packages) แต่แรงเสียดทานไปกองอยู่ที่สองจุด — endpoints ที่โตจนกลายเป็น service เสียเอง และ pages ที่ fetch + business logic + JSX ปนกัน และมี seams ที่ทำค้างไว้ 3 แห่ง: apiFetch (adopt แค่ ~3 ไฟล์), live-chat ที่ยกโค้ดออกแต่ยัง raise HTTPException ใน service, และ pseudonym contract ที่ยังเหลือ flag 3 สถานะทั้งที่เหลือสถานะเดียวที่ใช้ได้

คำศัพท์ที่ใช้ตลอดรายงาน (ตามหลัก codebase-design): module (หน่วยที่มี interface + การทำงานภายใน) · interface (ทุกสิ่งที่คนเรียกต้องรู้) · ความลึก (ความสามารถมากต่อ interface เล็ก) · seam (จุดที่เปลี่ยนพฤติกรรมได้โดยไม่ต้องแก้ที่นั่น) · adapter (ของจริงที่สวมเข้าที่ seam) · leverage (ผลตอบแทนของคนเรียก) · ความกระชับ (locality — แก้ที่เดียวจบ)

1. ServiceRequest — endpoint ที่กลายเป็น service เสียเอง

แนะนำ بقوة

ไฟล์ที่เกี่ยวข้อง: backend/app/api/v1/endpoints/admin_requests.py (720 บรรทัด), app/core/request_workflow.py, app/core/permissions.py

ปัญหา: ไม่มี request_service — endpoint คือ service: มี db.execute/select ตรง ๆ ~30 จุด, 6 Pydantic models นิยามในไฟล์, 4 stats queries, และ private helpers (_check_workflow_guards:370, _apply_status_and_assignment:436) ที่รับของ 3 ระดับพร้อมกัน (Pydantic + ORM + User) กฎการเปลี่ยนสถานะกระจายอยู่ 3 ที่: request_workflow.py (แผนที่สถานะ) + permissions.py (สิทธิ์) + ตัว endpoint (การบังคับใช้) — แก้หนึ่งการเปลี่ยนสถานะต้องแตะสามไฟล์ ผลการทดสอบการลบ: ลบ private helpers แล้วตรรกะจะไปเกิดซ้ำในทุก route — มันทำงานอยู่จริง แต่อยู่ผิดที่

แนวทาง: สร้าง ServiceRequestService ที่รับข้อมูลธรรมดาแล้วคืนผลลัพธ์: โอนย้าย queries, การเปลี่ยนสถานะตาม workflow, และการเขียน audit เข้าไป; endpoint เหลือแค่ตรวจสอบสิทธิ์ + เรียกใช้ + แปลง response

ผลดี: ความกระชับ — เครื่องสถานะทั้งเส้นอยู่ในไฟล์เดียว ทดสอบได้โดยไม่ต้องตั้ง HTTP; leverage — stats queries ทั้ง 4 ชุดเรียกใช้ซ้ำจากที่อื่นได้; interface กลายเป็นพื้นผิวของการทดสอบตรง ๆ

ก่อน — workflow กระจาย 3 ที่, ตรรกะฝังใน endpoint

admin_requests.py — interface ใหญ่: ~30 จุดแตะ DB + 6 schemas + 4 private helpers
ตื้น: ไม่มีอะไรซ่อน — ทุกอย่างโผล่ที่ผิว
request_workflow.py+permissions.py+endpoint helpers

หลัง — module เดียวลึก, endpoint บาง

2. กังวลเรื่อง HTTP รั่วเข้า live-chat service (seam ที่ทำค้าง)

แนะนำ بقوة

ไฟล์ที่เกี่ยวข้อง: backend/app/services/live_chat_service/sessions.py (raise HTTPException 7 จุด: บรรทัด 41, 61, 84, 119, 124, 158, 191), endpoints/admin_live_chat.py:264–281

ปัญหา: การแยก live_chat_service/ เป็น 10 โมดูล (จาก PR #137) ย้ายโค้ดสำเร็จแต่ย้ายเรื่อง HTTP ออกไม่หมด: ตัวบริการยังเลือก status code เอง แล้ว endpoint ก็จับ ValueError มาเทียบ ค่าสตริง เพื่อแปลงกลับเป็น status อีกรอบ — สองชั้นทำหน้าเดียวกัน

แนวทาง: บริการ raise domain exceptions (SessionAlreadyClaimed, NotSessionOperator) — ไม่มี from fastapi import ใน service; endpoint มีตัวแปลเป็น HTTP เพียงจุดเดียว

ผลดี: ทดสอบวงจรชีวิตของแชทผ่าน interface ของมันได้โดยไม่ต้องพึ่ง FastAPI; การแก้ข้อความ/รหัสสถานะทำที่เดียว — ความกระชับ; รอยต่อระหว่าง domain กับ transport ชัดขึ้นทั้ง 10 โมดูลใน package

ก่อน — แปล HTTP สองรอบ

service: raise HTTPException(409)
endpoint: catch ValueError
  → เทียบสตริง → ได้ status ใหม่

หลัง — domain exception แปลรอบเดียว

service: raise SessionAlreadyClaimed
endpoint: ตัวแปลตัวเดียว → 409
