## Recommendations in priority order

1. **Resolve reminder outcome classification before relying on automated retries in production.** The email helper returns false on every send exception, including a possible timeout after acceptance. That outcome can be retried. The LINE circuit breaker can reject a call before it reaches the provider, yet the notification layer treats the exception as unknown and the scheduler can record the reminder as sent. Carry separate outcomes for definite non-send, accepted, and unknown from the provider boundary. Check that the worker still owns an unexpired claim immediately before calling the provider. Finalization checks ownership after the send. Document the operational handling for unknown outcomes and expired claims. A worker that stops after provider acceptance can still be followed by another worker retrying after the five-minute lease. Verify a pre-send refusal, an ambiguous timeout, and a worker stop after acceptance. [Email send result](../../backend/app/services/booking_email.py#L85), [LINE circuit breaker](../../backend/app/services/line_service.py#L160), [Outcome mapping](../../backend/app/services/booking_notifications.py#L94), [Scheduler finalization](../../backend/app/tasks/booking_reminder.py#L121), [Lease duration](../../backend/app/services/booking_service.py#L552).
2. **Test the full case retry on a phone in LINE.** Confirm that a second deliberate submission gets another case number and a lost response followed by an unchanged retry leaves one case. The server currently replays based on identifier and owner before considering changed case content. There is no same-id, different-payload conflict test. Define behavior when a citizen edits the form after a lost response. Prefer an explicit conflict or recovery choice over a success message for the earlier content. Include the delayed attachment and hidden-email phone checks in the same release pass. [Replay lookup](../../backend/app/api/v1/endpoints/liff.py#L240), [Replay tests](../../backend/tests/test_liff_service_request_idempotency.py#L151), [Handoff phone checks](../claude_code/session-summary-20261121-1224.md#L35).
3. **Refresh the broadcast page after a late cancellation.** A completed or failed broadcast takes a validation branch that becomes HTTP 400. The page refreshes only on HTTP 409. Handle the stale-state response consistently and show the stored status to staff. Verify when sending finishes between page load and cancellation. The conditional database write already protects the final state. [Cancellation states](../../backend/app/services/broadcast_service.py#L317), [Response mapping](../../backend/app/api/v1/endpoints/admin_broadcast.py#L314), [Frontend refresh](../../frontend/app/admin/chatbot/broadcast/%5Bid%5D/page.tsx#L139).
4. **Tie release evidence to the proposed merge revision.** Record exact test counts and the final exit code for both Windows teardown and the normal CI suite. For manual deployment, apply the two migrations in order before deploying the new backend. The workflow makes automated backend deployment depend on the migration job, but the job skips the upgrade with a warning when `BACKEND_REMOTE_ENV_FILE` is absent. Confirm the migration actually ran in the release run. Plan the reminder-worker transition so old and new workers do not handle the same work under different claim rules. [Migration configuration check](../../.github/workflows/cd.yml#L264), [Reminder migration](../../backend/alembic/versions/f0a1b2c3d4e6_booking_reminder_claim_lease.py#L23), [Case migration](../../backend/alembic/versions/z2a3b4c5d6e7_service_request_submission_id.py#L15), [Migration job](../../.github/workflows/cd.yml#L311), [Backend deployment dependency](../../.github/workflows/cd.yml#L335).
